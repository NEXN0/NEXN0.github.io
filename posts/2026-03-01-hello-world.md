这个站点第一次上线是在一个很普通的周末下午。没有宏大的计划，只是想给自己的笔记找一个安放的地方：它能被分享，能被搜索，能在我换电脑之后依然存在。

## 为什么自己写

现成的博客框架已经足够好了。真要偷懒，Hexo、Hugo、Astro 随便挑一个，改改配置就能跑起来。但我想要的其实不多：

- 页面足够快，不需要等几秒钟的加载动画
- 想改哪里就能改哪里，不用和主题作者的审美博弈
- 内容用 Markdown 写，放在 Git 里，永远不会丢
- 部署只需要 `git push`

于是最后的方案非常朴素：**一个 300 行的 Node 脚本，把 Markdown 变成 HTML。**

## 它是怎么工作的

整个构建过程只有三步：

1. 读取 `posts/` 目录下的 Markdown 文件，解析开头的 front matter
2. 用自己写的渲染器把正文转成 HTML
3. 套上模板，写到 `dist/` 目录

没有依赖，没有 `node_modules`，没有构建缓存需要清理。

```js
// 构建的入口只有这一行
build();

if (process.argv.includes('--serve')) serve();
```

> 简单的好处是：半年之后回头看这份代码，依然看得懂。

## 目录结构

| 路径 | 作用 |
| --- | --- |
| `posts/` | 文章，一行 front matter 加正文 |
| `page/` | 关于、友链这类静态页面 |
| `src/styles/` | 全部样式，纯 CSS |
| `src/client/` | 主题切换、搜索这些小交互 |
| `scripts/` | 构建脚本与 Markdown 渲染器 |
| `dist/` | 构建产物，GitHub Pages 从这里读 |

## 一点取舍

:::note
写完渲染器之后我才意识到，CommonMark 的边界情况远比想象中多。这里只实现了自己真正会用到的那部分语法，遇到不支持的情况，就改写成 HTML。
:::

比如嵌套列表、表格对齐、代码块高亮，都是我手动测过、确认够用的程度。没有引入完整的 Markdown 解析库，是为了让「从 clone 到构建成功」这件事不需要网络。
